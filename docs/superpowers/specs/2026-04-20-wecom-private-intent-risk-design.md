# 企微私域意图判断与风险识别设计

## 文档定位

这份设计文档定义的是企微私域客服流程中的下一步能力：

- `意图判断与风险识别`

它承接已经完成的：

- 固定二维码与私域 lead 建档
- AI 自动接待配置与运行时编排
- 用户识别与粗分层

这份设计要解决的是：

1. 在 `wecomprivate` 会话里，系统如何对每条用户消息做结构化意图和风险判断
2. 这些判断结果应该落在哪些后端模型上，如何复用现有 `service_desk` / `wecom_private` 边界
3. 第一版应该做到“判断到什么程度”，以及哪些动作明确留给后续“智能分流”去执行
4. 客服台如何看到这些结果，便于人工接手前快速理解上下文

这份文档不是实施清单。具体编码任务拆分放在后续 implementation plan 中。

---

## 一、已确认前提

基于当前对话、既有蓝图和已完成的第二、三步实现，后续设计遵循以下前提：

1. 当前仍只服务 `wecomprivate`
2. 当前产品模型仍保持：
   - `bot = 接待入口`
   - `pipeline = 接待模板`
   - `bot config = 入口规则覆盖`
3. 当前客服主链路已存在三类会改变行为的逻辑：
   - 人工关键词直转
   - 绑定补录触发
   - 连续未解决兜底
4. 第三步已完成“用户识别与分层”，并已在 `WecomPrivateLead` 上沉淀：
   - `profile_status`
   - `user_layer`
   - `layer_source`
   - `profile_signals`
5. 当前还没有游戏侧实时画像回流，因此第四步不能依赖外部实时等级、充值或封禁真值
6. 第一版重点是“先判断对、先可见、先可复盘”，而不是立即做激进的自动执行
7. 用户已明确选择：
   - 第四步先做结构化识别结果与推荐动作
   - 不在第四步直接改路由行为

---

## 二、目标与非目标

### 2.1 目标

构建一层规则优先的识别能力，使系统在 `wecomprivate` 会话中具备以下能力：

- 对用户当前消息给出结构化意图标签
- 对当前会话给出风险等级判断
- 给出推荐动作，但不直接执行自动分流
- 把识别结果持久化，供第五步“智能分流”直接消费
- 在现有客服台中向人工展示“用户现在在问什么、风险高不高、系统建议怎么处理”

### 2.2 非目标

本次设计明确不做以下内容：

- 不直接把第四步结果改造成自动转人工
- 不在这一版引入 LLM 分类器或大模型裁决
- 不做复杂风险评分模型
- 不做工作台列表按风险/意图筛选
- 不做人手工改意图、改风险等级的后台能力
- 不做运营动作联动

---

## 三、推荐方案

### 方案 A：规则优先的结构化识别层，不直接改路由行为

这是本次推荐方案。

核心思路：

- 继续复用 `ServiceDeskService.handle_incoming_message` 作为接待前置编排入口
- 在现有 routing 逻辑之前或过程中增加一层“识别判断”
- 产出结构化结果：
  - `intent_label`
  - `risk_level`
  - `risk_reasons`
  - `recommended_action`
  - `confidence`
- 把结果落盘，并同步更新 `ServiceDeskSession.risk_level`
- 不改变现有 `queue_status` / `handoff_reason` / `mode`

优点：

- 与流程图天然一致：第四步负责“判断”，第五步负责“分流”
- 对现有逻辑入侵最小，不容易打乱第二步已上线链路
- 结果可见、可复盘、可调优，后续容易演进

缺点：

- 第一版不会立刻表现为“会自动转人工更聪明了”
- 第五步还需要再消费这些结果，才能形成完整自动分流

### 方案 B：第四步识别完后，直接顺手改路由行为

核心思路：

- 一旦命中高风险或明确投诉，就在第四步直接把会话切到 `pending_manual`

优点：

- 业务表现更直接

缺点：

- 会把第四步和第五步揉成一层
- 会与现有“关键词转人工 / 补录触发 / 未解决兜底”形成叠加和冲突
- 第一版难以定位误判到底来自识别层还是分流层

### 方案 C：直接接 LLM 做意图/风险分类

核心思路：

- 用大模型对消息和上下文做分类，再输出结构化标签

优点：

- 长期潜力更高

缺点：

- 第一版成本和不确定性过高
- 输出稳定性、调试难度和测试成本都明显变差

### 结论

本次采用 `方案 A：规则优先的结构化识别层，不直接改路由行为`。

## 四、核心产品模型

### 4.1 第四步的职责

第四步只负责回答四个问题：

1. 用户这条消息主要属于什么意图
2. 当前会话风险有多高
3. 为什么这样判断
4. 系统推荐继续 AI、建议人工，还是先要求补录绑定

第四步不负责回答：

- 现在就转不转人工
- 现在就改不改 `queue_status`
- 现在就触发哪条自动分流规则

这些属于第五步“智能分流”的职责。

### 4.2 与第三步的关系

第三步沉淀的是“这个用户是谁、处于什么层级”；第四步关注的是“这次来找我们干什么、风险高不高”。

两者关系如下：

- `WecomPrivateLead`
  - 提供用户画像基础：`profile_status / user_layer / profile_signals`
- 第四步识别结果
  - 提供会话级判断：`intent / risk / recommended_action`

这两个维度必须继续分离，不能重新混回一个字段。

## 五、结构化识别结果设计

### 5.1 结果字段

第一版统一产出以下结果：

- `intent_label`
  - 当前建议枚举：
    - `general_consult`
    - `binding_request`
    - `payment_issue`
    - `compensation_issue`
    - `complaint`
    - `vip_request`
    - `other`
- `risk_level`
  - `low / medium / high`
- `risk_reasons`
  - 规则命中原因列表，例如：
    - `complaint_keyword`
    - `payment_keyword`
    - `high_emotion_keyword`
    - `vip_user_layer`
    - `binding_missing_for_payment`
- `recommended_action`
  - `continue_ai`
  - `suggest_manual`
  - `require_binding`
- `confidence`
  - 第一版仍保留字段，但固定为规则口径下的高置信值，如 `1.0` 或预定义映射

### 5.2 第一版规则口径

第一版不追求覆盖所有传奇客服场景，只先覆盖业务价值最高、误伤成本最低的几类：

- `binding_request`
  - 消息里出现 UID / 区服 / 角色名 / 查号 / 角色 / 账号 等明显绑定语义
- `payment_issue`
  - 消息里出现充值、未到账、扣款、补单、返利等语义
- `compensation_issue`
  - 消息里出现补偿、掉线补偿、维护补偿、赔偿等语义
- `complaint`
  - 消息里出现投诉、举报、退款、骗、垃圾、差评、骂人等高风险投诉语义
- `vip_request`
  - 用户层级是 `vip / big_r`，或消息里明确出现 VIP、专属客服、大R 等语义
- 默认归为 `general_consult`

### 5.3 风险等级口径

第一版建议如下：

- `high`
  - 命中投诉类关键词
  - 命中明显高情绪或高风险维权语义
- `medium`
  - 命中充值/补偿问题
  - 命中 VIP / 大R 诉求
- `low`
  - 普通咨询、普通绑定补录

### 5.4 推荐动作口径

第一版推荐动作按以下规则生成：

- `require_binding`
  - 当前意图是 `payment_issue / compensation_issue`
  - 且 lead 还没有完成有效绑定
- `suggest_manual`
  - 风险等级为 `high`
  - 或用户层级已是 `vip / big_r`
- `continue_ai`
  - 其他情况

这个动作目前只用于展示和后续消费，不直接改变会话状态。

## 六、数据与持久化设计

### 6.1 Session 侧复用

继续复用已有 `ServiceDeskSession.risk_level` 字段，保存当前会话最新风险等级。

第一版不新增 `intent_label` 到 `ServiceDeskSession`，避免会话主表承载过多瞬时识别信息。

### 6.2 新增识别记录模型

第一版建议新增独立表，例如：

- `WecomPrivateIntentRiskRecord`

建议字段：

- `id`
- `session_id`
- `message_id`
- `intent_label`
- `risk_level`
- `risk_reasons`
- `recommended_action`
- `confidence`
- `created_at`

用途：

- 保留每次识别结果
- 支撑客服台展示最新识别结果
- 为第五步“智能分流”提供直接可消费的结构化输入
- 便于后续复盘误判和调规则

### 6.3 Overlay 聚合

`wecom_private_service.get_session_overlay` 继续作为私域附加信息聚合出口。

在现有：

- `lead`
- `routing_decisions`
- `binding_task`
- `closure_record`

基础上，新增：

- `latest_intent_risk_record`
- 如有必要，后续再扩展 `intent_risk_records`

第一版前端只看最新结果，不显示全历史列表。

## 七、运行时设计

### 7.1 挂载位置

第四步仍然挂在现有 `ServiceDeskService.handle_incoming_message` 主链路中。

推荐执行顺序：

1. 基础 session 恢复与 reopen 判断
2. 若会话已在 `manual / pending_manual`，继续沿用现有短路逻辑
3. 对当前消息执行意图与风险识别
4. 更新最新识别记录和 `session.risk_level`
5. 再进入现有：
   - material 命中
   - handoff keyword
   - binding 补录
   - unresolved fallback
   - continue_ai

### 7.2 为什么不直接替换现有逻辑

因为现有逻辑已经承担了“真正改变行为”的职责：

- 关键词转人工
- 绑定补录触发
- 连续未解决兜底

第四步若第一版就直接替换这些行为，会让排障和回归风险急剧上升。

所以第一版只补“识别”，不抢“执行”。

### 7.3 输入来源

识别函数应至少消费以下输入：

- 当前用户消息文本
- `WecomPrivateLead`
  - `profile_status`
  - `user_layer`
  - `profile_signals`
- 当前 `binding_task`
- 当前 session 的 `unresolved_count`

这样规则才能结合“说了什么”和“这个人是谁”一起判断。

## 八、客服台展示设计

第一版继续只复用 `SessionDetail`，不新增独立工作台页面。

建议增加一块新的卡片：

- `意图与风险`

展示内容包括：

- 最新意图标签
- 当前风险等级
- 推荐动作
- 命中原因
- 识别时间

这块卡片的价值是：

- 人工看到会话时，先知道“这个人是在咨询、投诉还是充值补偿”
- 不必仅靠 routing record 去反推用户当前问题
- 为后续第五步落地自动分流前，先让人工和运营看到系统判断是否靠谱

第一版不做：

- 按意图/风险筛选工作台列表
- 识别历史时间轴
- 人工手工修改识别结果

## 九、验收标准

### 9.1 业务验收

必须满足：

1. 用户每条私域消息都可以得到一条结构化识别结果
2. 客服台会话详情能看到最新意图和风险结果
3. 高风险或高价值用户能显示为 `suggest_manual`，但不会在第四步自动转人工
4. 充值/补偿类且未绑定用户能显示为 `require_binding`

### 9.2 数据验收

必须满足：

1. `ServiceDeskSession.risk_level` 会同步保存最新风险等级
2. 至少有一张独立记录表持久化识别结果
3. `get_session_detail` 或相应 overlay 能返回最新识别结果

### 9.3 回归验收

必须满足：

1. 现有人工关键词转人工逻辑不回归
2. 现有 binding 补录触发逻辑不回归
3. 现有 unresolved fallback 逻辑不回归

## 十、风险与约束

### 风险 1：规则口径过窄

影响：

- 第一版识别覆盖有限，很多消息会落到 `general_consult`

应对：

- 接受第一版先做高价值、高确定性场景
- 把扩展规则留到后续版本

### 风险 2：第四步和第五步边界再次混淆

影响：

- 很容易在实现时顺手把推荐动作直接做成自动分流

应对：

- 在 spec 和 plan 中明确：
  - 第四步只更新结构化结果
  - 第五步才消费这些结果去改路由

### 风险 3：规则与现有关键词转人工重叠

影响：

- 可能出现同一条消息既命中“建议人工”，又命中现有 handoff keyword

应对：

- 第一版允许两者并存
- 真正改变行为的仍以现有转人工逻辑为准
- 第四步记录结果主要服务可见性和后续消费

---

## 十一、结论

第四步第一版的最佳落地方式是：

- 做一层规则优先的结构化识别
- 保存意图、风险、推荐动作和命中原因
- 同步更新会话风险等级
- 在现有客服台会话详情中展示最新识别结果
- 不在这一版直接改变路由行为

这意味着当前最合理的推进顺序是：

- 第四步：先判断、先存储、先可见
- 第五步：再根据第四步结果做真正的智能分流

这样可以在不打乱已完成链路的前提下，逐步把私域接待从“规则堆叠”推进到“可解释的智能分流”。
